# ADR-003: Redwood Treehouse Is the Existence Proof for Compose-in-QuickJS; External Evidence Refresh

**Date:** 2026-08-31
**Status:** Accepted

## 1. Context & Problem Statement

Three load-bearing external claims in the version 4.0 documents were checked during adversarial review and found stale or overstated:

1. [`roadmap.md`](../../roadmap.md) Phase 0.2 claimed "Nobody has run Compose composition in a JavaScript interpreter" — while [Layer 4](../../specs/layer-4-sandbox.md) section 2 simultaneously (and correctly) stated the Compose runtime is "confirmed in production use on a JavaScript guest by Cash App's Redwood." The documents contradicted each other.
2. The risk register treated the reason for Redwood's discontinuation as unknown and "requiring a conversation rather than a search."
3. The Apple App Store compliance discussion cited Guideline 2.5.2's JavaScriptCore exception as the governing text.

## 2. Decision

1. **Phase 0.2 is reframed from an existence question to a measurement question, and its cheapest form is to instrument Redwood's working samples.** Redwood's Treehouse verifiably ran Google's real `androidx.compose.runtime` (Kotlin/JavaScript target) inside Zipline's QuickJS on device. What has never been published is a *performance number* for composition or recomposition in that configuration. Phase 0.2 therefore starts from the runnable `counter` and `emoji-search` Treehouse samples rather than building a harness from scratch.
2. **The Redwood-discontinuation risk is downgraded from "unknown, material" to "publicly characterised, residual."** Redwood's maintainer stated the shutdown decision was not technical. Confirming the fuller story with Cash App remains worthwhile but is no longer a top-priority open action.
3. **The App Store compliance analysis is re-anchored on the current guideline text.** The explicit "run by Apple's built-in WebKit framework or JavascriptCore" exception sentence no longer appears in Guideline 2.5.2; downloaded scripting is now addressed by Guideline 4.7 (mini apps, mini games, and plug-ins, conditions 4.7.1–4.7.5). The Developer Technical Support inquiry planned in Phase 0 must reference 4.7, and the risk remains open: precedent exists, but no written Apple ruling does.
4. **Compose Multiplatform platform-status statements are pinned to verified facts** (see section 3) — in particular, the Web target is **Beta**, not stable, and this must be stated wherever Web reach is claimed.

## 3. Rationale & Research

**Treehouse ran Compose in QuickJS — verified at source level.**
- [`redwood-compose/build.gradle`](https://github.com/cashapp/redwood/blob/trunk/redwood-compose/build.gradle) declares `api libs.androidx.compose.runtime` in `commonMain` with a JavaScript target; [`gradle/libs.versions.toml`](https://github.com/cashapp/redwood/blob/trunk/gradle/libs.versions.toml) resolves it to Google's Kotlin Multiplatform artifact `androidx.compose.runtime:runtime:1.9.4`.
- [`samples/emoji-search`](https://github.com/cashapp/redwood/tree/trunk/samples/emoji-search) contains a `presenter` module (`@Composable` code compiled with the Compose compiler plugin for a JavaScript target, depending on `redwoodTreehouse` and `redwoodTreehouseGuestCompose`) plus Android, iOS (UIKit host), and browser host applications. A `counter` sample also exists. Demonstrated publicly at KotlinConf 2023: [Playing in the Treehouse with Redwood and Zipline](https://jakewharton.com/playing-in-the-treehouse-with-redwood-and-zipline/).
- Production extent: Cash App's July 2023 post ([Native UI and multiplatform Compose with Redwood](https://code.cash.app/native-ui-and-multiplatform-compose-with-redwood)) describes limited usage rolling out; Zipline/QuickJS itself ships "to millions of our customers" ([zipline#1654](https://github.com/cashapp/zipline/issues/1654)). Full-scale Treehouse UI deployment specifics: **UNPROVEN**.
- Published composition/recomposition performance measurements inside QuickJS: **none found.** The only published numbers are module-load times ([How We Sped Up Zipline Hot Reload](https://code.cash.app/how-we-sped-up-zipline-hot-reload)). Phase 0.2's benchmark is therefore still necessary; only its "nobody has run it" framing was wrong.

**Redwood's discontinuation is publicly characterised.** The [README](https://github.com/cashapp/redwood/blob/trunk/README.md) states "This project is no longer under active development"; the final release is 0.19.0 (2025-11-06), announced in [discussion #2894](https://github.com/cashapp/redwood/discussions/2894) ("This will be the final release of Redwood for the foreseeable future"), where maintainer Jake Wharton wrote: **"The decision wasn't technical. Redwood works/worked great for its intended use cases."** This aligns with the second-hand account recorded in [Layer 5 ADR-004](../layer-5/ADR-004-compose-multiplatform-sole-host-target.md) and removes the "silent technical verdict" scenario, though the organisational-adoption lesson it carries applies to Dogwood with full force.

**App Store guideline text — verified against the [current guidelines](https://developer.apple.com/app-store/review/guidelines/).** Guideline 2.5.2 now reads that apps "should be self-contained in their bundles" and may not "download, install, or execute code which introduces or changes features or functionality of the app," with an educational-apps carve-out; the JavaScriptCore exception sentence formerly quoted is absent. Guideline 4.7 permits mini apps and plug-in content under conditions 4.7.1–4.7.5. Cash App's shipping of Zipline-delivered JavaScript to a bundled QuickJS remains the strongest precedent; formal approval-safety remains **UNPROVEN**.

**Compose Multiplatform status (verified August 2026).** iOS: Stable since [1.8.0 (May 2025)](https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/), which also publishes the figure that Compose Multiplatform adds **roughly 9 megabytes** to an iOS application versus a SwiftUI equivalent. Web: **Beta** since [1.9.0 (September 2025)](https://blog.jetbrains.com/kotlin/2025/09/compose-multiplatform-1-9-0-compose-for-web-beta/), still Beta per [the Kotlin platform-stability page](https://kotlinlang.org/docs/multiplatform/supported-platforms.html). Latest release: [1.12.0 (August 2026)](https://blog.jetbrains.com/kotlin/2026/08/compose-multiplatform-1-12-0/). Maven Central: `org.jetbrains.compose.ui:ui-wasm-js` and `foundation-wasm-js` at 1.12.0, but `material3-wasm-js` latest is **1.12.0-alpha03** — the Material 3 Web artifact lags the stable line. Google's Maven ([runtime group index](https://dl.google.com/android/maven2/androidx/compose/runtime/group-index.xml)) confirms `runtime-js` and `runtime-saveable-js` exist through 1.12.0 stable, and that no `ui-js`/`foundation-js`/`material3-js` artifacts exist from Google — the architecture's premise about which halves of Compose reach JavaScript is sound. Embedding Compose into an existing SwiftUI application is officially documented ([SwiftUI integration](https://kotlinlang.org/docs/multiplatform/compose-swiftui-integration.html)), with the documented `CADisableMinimumFrameDurationOnPhone` Info.plist requirement.

**Fallback substrate, recorded for the Phase 0 gate.** If QuickJS fails the recomposition budget, the strongest alternative interpreter identified is Meta's **Hermes**: ahead-of-time bytecode compilation is core to its design ([Hermes announcement](https://engineering.fb.com/2019/07/12/android/hermes/); [Features.md](https://github.com/facebook/hermes/blob/main/doc/Features.md)), and it is actively maintained (commits within days as of August 2026). Two caveats, both **UNPROVEN**: shipping Hermes still lists some ECMAScript 2015 features (classes) as planned, while Kotlin/JavaScript emits ECMAScript 5 by default with 2015 opt-in ([Kotlin/JS docs](https://kotlinlang.org/docs/js-project-setup.html)) — plausibly compatible, never demonstrated; and embedding Hermes outside React Native is possible but not an officially supported product. Adopting it would also forfeit Zipline's loader, signing, and bridge, which would need rebuilding. JavaScriptCore in-process on iOS is interpreter-only without the just-in-time entitlement and exposes no bytecode-caching Application Programming Interface (API), so it forfeits the precompiled-bytecode startup win. None of this changes the QuickJS decision today; it defines the reopening path.

## 4. Unstated Assumptions

- **Assumes the Treehouse samples still build against current Zipline and can be instrumented within the Phase 0.2 budget.** Redwood is unmaintained; a pinned older toolchain may be needed. If the samples cannot be revived in roughly a day, fall back to the from-scratch harness in the original Phase 0.2.
- **Assumes Treehouse's guest workload is representative enough for a first bound.** Its widget protocol is smaller than Dogwood's generated surface; numbers from it are a floor for feasibility, not a forecast of Dogwood's cost. Dogwood-shaped stubs (deferred-expression recording) must still be measured in Phase 0.2 proper.
- **Assumes Guideline 4.7's "mini apps" language covers first-party signed payloads.** Apple's guidelines are interpreted by review, not by text alone; the Developer Technical Support ruling remains the required evidence.
