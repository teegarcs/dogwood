# ADR-005: Corrected Coverage Measurement (Third Revision) and the Re-Enumerated Bespoke Subsystem List

**Date:** 2026-08-31
**Status:** Accepted

## 1. Context & Problem Statement

Project Dogwood's economic thesis rests on a measured claim: that the overwhelming majority of the Compose Application Programming Interface (API) surface can be *generated*, leaving only a bounded, enumerable set of hand-written subsystems. The second revision of that measurement (recorded in [ADR-003](ADR-003-opaque-handle-binding-surface.md)) reported 450 composables in scope with **81.1% generable once the `Modifier` subsystem exists**, and the specifications enumerated exactly **six** bespoke subsystems.

Adversarial re-review of the committed classifier ([`tools/measure-compose-surface.py`](../../tools/measure-compose-surface.py)) found that this second measurement — like the first, which it corrected — was wrong in a direction that flattered the project. Because the review process has now produced two consecutive optimistic measurements, this Architecture Decision Record (ADR) also records the methodological safeguard adopted against a third.

## 2. Decision

1. **The coverage figures are corrected.** Over the same ten metalava dumps pinned to androidx commit `5bd169266a7ea9b28c5caf2c040e021677a7adc0`, of **445** public uppercase (widget-shaped) `@Composable` User Interface (UI) functions in scope: **67.6% (301) are generable once the `Modifier` subsystem exists**, **25.2% (112) require a bespoke subsystem** (live-state protocol, callback-object protocol, assets, or text input), and **7.2% (32) are structurally unreachable**. The 81.1% figure is **withdrawn**.
2. **The generable tier is gated on two subsystems, not one.** 230 of the 301 generable composables (76.4%) carry at least one deferred-expression parameter, so their full use requires the deferred-expression protocol as well as `Modifier`. "Generable after `Modifier`" must always be quoted with this caveat.
3. **The measured denominator is declared honestly.** The classifier measures the uppercase, widget-shaped surface only. The lowercase `@Composable` surface at the same commit is **458 functions — roughly the same size again — and is reported, not classified**: ~305 defaults factories and getters (ride on the deferred-expression protocol), 76 `remember*` state factories (each implies a live-state protocol entry), 34 animation-state functions (`animateFloatAsState`, `updateTransition`, and relatives — require the host-side animation subsystem), 14 `*Resource` loaders (require the resources subsystem), and 25 guest-runtime functions that work in the guest as-is.
4. **The bespoke subsystem list is re-enumerated from six to nine.** The three additions, each surfaced because the previous measurement was blind to it:
   - **7. Animation.** The specification promises "animation targets are declared and run host-side," but no listed subsystem carried that protocol, and the entire `animate*AsState` / `updateTransition` / `Animatable` authoring surface is lowercase and was never measured. A declarative animation protocol — target, duration, easing/spring parameters, interruption semantics, completion events, and time-varying `Modifier` values — is a hand-written subsystem at least the size of text input. Until it ships, [Layer 1](../../specs/layer-1-authoring.md)'s checker must reject animation APIs rather than let them silently tick per-frame in the guest.
   - **8. Resources and assets.** `Image` and `Icon` take a required `Painter`/`ImageBitmap`/`ImageVector` no deferred expression can produce: the sandboxed guest has no filesystem, no network, and no host resource identifiers. Fonts and localized strings share the problem, and `DogwoodConfiguration` carried no locale. Redwood's answer — the guest passes a Uniform Resource Locator (URL) string and the host widget loads it (verified: [`RedwoodUiBasic.kt`](https://github.com/cashapp/redwood/blob/trunk/redwood-ui-basic-schema/src/main/kotlin/app/cash/redwood/ui/basic/RedwoodUiBasic.kt) declares `Image(url: String, ...)`; host loaders in `redwood-ui-basic-uiview`/`-composeui`/`-view`) — is the model to adopt: a URL-keyed host image-loading protocol, an icon tag dictionary, payload-carried or host-resolved strings, and `locale` added to the configuration flow.
   - **9. Host services, entry points, and host-registered components.** How an experience is launched with parameters, which standard services (network, authentication, analytics, logging, feature flags, clock) the host exposes and how they version, and how a host application registers its *own* composables (design-system components, video, maps) into the dictionary with its own namespaced tag space (refined into per-module dictionary segments by [ADR-006](ADR-006-guest-composed-vs-host-registered-and-multi-design-system.md)). The generator's parser can be run over the host's own modules to produce this; the mechanism must be specified, not assumed.
5. **Classifier fixes adopted** (all committed in [`tools/measure-compose-surface.py`](../../tools/measure-compose-surface.py)):
   - Annotations are stripped before name capture. The previous revision captured annotation names as function names for 5 rows (`rememberDatePickerState` counted as a composable named `RequiresApi`), which is why the denominator falls from 450 to 445.
   - The unknown-type default is no longer silently generable. ~30 live-state holder types missing from `LIVE_STATE` (`TimePickerState`, `SliderState`, `RangeSliderState`, `CarouselState`, `DatePickerState`, `PullToRefreshState`, `SwipeToDismissBoxState`, `MutableTransitionState`, `Transition`, `SnackbarData`, and relatives), a new `CALLBACK_OBJ` class for objects carrying host-invoked callbacks (`KeyboardActions`, `VisualTransformation`, `InputTransformation`, `PopupPositionProvider`, `ColorProducer` — invoked per keystroke, per layout, or per draw), and a new `ASSET` class (`Painter`, `ImageBitmap`, `ImageVector`) are classified as bespoke when required.
   - Controlled text-input widgets (`TextField`, `OutlinedTextField`, `BasicTextField`, `SecureTextField`, `SearchBar`, and relatives) are excluded **by name**. The previous revision caught only their `TextFieldState` overloads; the `String value` + `onValueChange` overloads — exactly the controlled component [Layer 5](../../specs/layer-5-host.md)'s own exclusion table forbids — were counted generable.
   - `ENGINE` gains `MultiContentMeasurePolicy`, `LazyLayoutMeasurePolicy`, `GraphicsLayer`, `PlatformTextInputInterceptor`, `SubcomposeLayoutState`, and `Any` keys.
6. **`DropdownMenu` is reclassified as plausibly generable.** Its public parameters are a `Boolean`, a dismiss event, an offset, an optional `ScrollState` (live-state, optional), and `PopupProperties`. The Layer 5 exclusion table's listing of it alongside `HorizontalPager` was wrong and is corrected.

## 3. Rationale & Research

Every count above is reproducible: run `python3 tools/measure-compose-surface.py` against the pinned dumps. The two defects were one-directional. First, `if not name[:1].isupper(): continue` silently discarded 458 of 903 current `@Composable` functions (50.7% of the true surface) — including the *entire* authoring surface of `animation-core`, while "ten modules measured" implied that module was covered. Second, `classify_param()` returned `GEN_deferred_expr` — generable — for **any** type head not on a hand-maintained list, so every type nobody had thought about counted toward the headline. `Icon` and `Image`, arguably the two most-used media composables in existence, were counted "generable after `Modifier`" while the guest had no way to produce their required first argument.

The methodological safeguard: **the classifier must fail closed.** Unknown object types now still default to deferred-expression (that default is what makes the measurement possible at all), but the change from six to nine subsystems came from auditing what fell through that default, and the audit script's distinct-type-head enumeration should be re-run whenever the pinned commit moves, with new heads triaged into `LIVE_STATE` / `CALLBACK_OBJ` / `ASSET` / `ENGINE` before the headline is re-quoted.

**Why the thesis survives the correction.** The claim that must hold is not "81% is generated" but "the hand-written set is bounded and enumerable, and the generated set grows with Compose while the hand-written set does not." Nine subsystems is still a bounded list; 67.6% of the widget surface plus ~305 defaults factories via one deferred-expression protocol is still far beyond any hand-maintained SDUI registry. What does *not* survive is the claim that Dogwood needs "the same six" subsystems Redwood needed, or any framing of the bespoke tier as a minor remainder: at 25.2% of the widget surface plus three of the largest subsystems (animation, resources, text input), the bespoke half is confirmed as **the larger half of the work**, as the roadmap already stated.

## 4. Unstated Assumptions

- **Assumes the corrected constants are now complete enough.** They were audited against the pinned dumps, but the fail-closed triage described above is the guarantee mechanism, not any single audit.
- **Assumes the androidx Android dumps remain a usable proxy for the Compose Multiplatform common surface.** Unchanged from ADR-003, and still requiring re-measurement against `compose-multiplatform-core` before the numbers become product commitments.
- **Assumes the lowercase defaults-factory surface (~305 functions) is fully carried by the deferred-expression protocol.** That protocol has no ADR yet; if its grammar cannot express some factory forms, those functions shift into bespoke work.
- **Assumes an icon dictionary is enumerable.** `Icons.Default.*` are `val` properties, invisible to a function classifier; their count is unmeasured.
