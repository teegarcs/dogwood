# ADR-048: The Real Guest Runs on the Web, and the Screens Are Shared

**Date:** 2026-09-06
**Status:** Accepted

## 1. Context & Problem Statement

[`plans/production-readiness.md`](../../plans/production-readiness.md) §2.1 called this the largest
hole in the alignment story, and the web slice's own guest said so in its header:

> It is NOT what a real guest is: a real guest is Kotlin compiled to JavaScript, running a Compose
> composition, with `dogwood-compose`'s applier producing the batch.

That hand-written guest was the right thing to build. A guest written by hand, in JavaScript, is
what proves the protocol is an **interface** rather than an artefact of having Kotlin on both ends.
What it could not prove is that real guest code runs there at all — so every web conformance claim
was graded against either shared host code or a guest no product would ever write, and the
architecture's central claim had no demonstration on one of its three shipping targets.

There was a structural reason it had never been tried. The screens lived inside `slice-guest`, which
is the **mobile** guest: a Kotlin/JavaScript executable loaded into QuickJS by Zipline. Any other
entry point would have had to copy them.

## 2. Decision

**The screens move to `samples/slice-screens`, and both entry points depend on them.**

`slice-guest` becomes what it always was underneath — an entry point that binds a `DogwoodGuest` to
a Zipline service. `samples/web-guest` is the second one: the same `DogwoodGuest`, the same screens,
driven from a Web Worker. **The screens do not know which.** Nothing in that module names Zipline,
`postMessage`, or a platform. `ExploreParams` moved with them, because a launch parameter is part of
what a screen needs and not part of how a payload was delivered.

**The platform difference is one interface with five methods.** `DogwoodHost` is the guest's egress;
on mobile it is a Zipline service and here it carries a batch to `postMessage`. Everything above it
— `DogwoodComposition`, the applier, the recorder, `rememberSaveable`, every generated stub — is the
same code.

**Both guests stay, and the page chooses with a sidecar.** `dogwood-manifest.json` names the
hand-written one; `dogwood-manifest-kotlin.json` names the real one. Deleting the hand-written guest
would delete the only evidence that the protocol is writable by something that is not this codebase.

**A product's design system must target every platform its hosts run on.** That is obvious once
stated and was invisible while every host was a Java Virtual Machine one — `samples/product-design-system`
gains a `wasmJs` target and the web page registers Acme exactly as the Android host does.

## 3. Rationale & Research

### Verified in a real browser, and the report is the argument

Headless Chrome, the shipped page, the real guest:

| Observation | Result |
|---|---|
| First batch | **93 nodes** — the sample's whole About screen, composed in a Worker |
| What is in it | section headers, a masked `TextInput`, a `ScrollArea` with 24 clauses, animated modifiers, host-resolved formats |
| A product's components | `AcmePanel`, `AcmePrice`, `AcmeAction` — named, from segment 2, after the web host registered them |
| Rendered | `renderedNodes: 27` — the host composed the tree, not merely applied it |
| Event → recomposition | tap node 22, and the answering batch is `[[1,19,11,true],[1,19,12,1]]` |
| Saved state | `rememberSaveable` round-tripped a scroll quantum and a focus count |

That answering batch is worth reading. Node 19 is the `TextInput`; properties 11 and 12 are
`focusRequested` and `focusSequence`. **A live-state holder, declared on a surface, generated by
`@Holder`, crossed from a real Compose composition running in a Web Worker.** Every subsystem in the
architecture is in that one line.

### Three defects, and none of them was where it looked

**The `onmessage` shim resolved a minified name.** `js("self.onmessage = function (e) { dogwoodOnMessage(e.data); };")`
compiles and then fails at runtime: the identifier inside the string is resolved by the JavaScript
engine against the *minified* module scope, where the function is not called what the source called
it. The symptom was a guest that announced itself and then never sent a batch — which reads exactly
like a composition that produced nothing. Binding a Kotlin function reference fixes it.

**The web page's harness looked for a shape only one guest produced.** It hunted for a clickable
`Row`, which the hand-written guest builds and the About screen does not, and reported "the event
path was not exercised" — true, and it reads like an absence of buttons rather than an absence of
*rows*. It now accepts an enabled `PrimaryButton` too.

**And the one that was not a defect at all.** The guest requested frames and the host never answered,
which looked like a broken bridge. It was the probe's own Chrome flags: without
`--enable-unsafe-swiftshader` and the backgrounding disables, `requestAnimationFrame` never fires,
so the host's frame pump never runs. This project's own harness has carried those flags all along.
The hand-written guest answers an event synchronously and needs no frame, so **nothing had ever
depended on a frame arriving** — the first real Compose guest was always going to be the thing that
found it. Reproducing against the real thing before changing course is what kept a correct bridge
from being "fixed".

### What the guest costs

| Script | Raw | brotli |
|---|---:|---:|
| hand-written `guest.js` | 8,844 | 2,928 |
| real `guest-kotlin.js` | 897,823 | **201,458** |

201 KB brotli, on a page that is already 3.58 MB, is **5.6%** — and it is not on the critical path
for the first frame the way the renderer is, because the Worker starts after the sidecar check.
Recorded rather than gated: `G5` measures the page, and this is a second artifact whose budget is a
question the web profile has not been asked yet.

## 4. Unstated Assumptions

- **The service surface is thin, and honestly so.** `WorkerServices` answers `log` locally and
  declares everything else absent. Network, clock, analytics, feature flags and navigation over the
  Worker bridge are [ADR-032](ADR-032-the-web-profile.md)'s remaining work; every screen degrades
  when a service is missing, which is why the About screen renders "host clock unavailable" rather
  than failing.
- **Launch parameters are not carried yet.** The Worker guest passes `JsonNull`, so `explore` and
  `app` compose with defaults. The mobile path carries them through the manifest's entry point.
- **Segment versions are not carried yet either.** The guest is handed an empty map, so a screen
  branching on client capability sees none. The sidecar already carries them for the *dictionary
  check*; wiring them into `start()` is small and is not done.
- **A code update has not been exercised on web.** The mobile path replaces a guest generation and
  restores state; the Worker path can in principle do the same, and nothing has tried.
- **The envelope is mirrored, not shared.** The host is Kotlin/WebAssembly and the guest is
  Kotlin/JavaScript; they do not link. The revision check is what makes a drifted mirror a refusal
  rather than a guess.
