# ADR-057: A whole product outside the repository, and what its first build found

**Date:** 2026-09-07
**Status:** Accepted

## 1. Context & Problem Statement

The adoption audit ([`plans/adoption-audit.md`](../../plans/adoption-audit.md) A2) observed that no
build outside this repository had ever produced a **payload**. `tools/standalone-check` proved the
host half — a design system compiling against published artifacts — while the guest toolchain
(`dogwood-compose` from a repository, generated guest stubs, the Zipline plugin, signing) had never
been assembled anywhere a path dependency could not paper over a hole. The claim "a product outside
this repository can use Dogwood" was half-proven, and the unproven half is the half a product ships.

One constraint from the owner: a genuinely external exercise is not available, so the proof lives in
this repository, **deliberately disconnected from the Dogwood source** — its own Gradle build, no
`includeBuild`, no path into `engine/`, everything by coordinate from a repository.

## 2. Decision

**Umbra is a whole product now** — three modules in one standalone build:

| Module | What it is | What it resolves |
|---|---|---|
| `:design` | Umbra's component surface; host bindings and guest stubs generated by the Dogwood plugin | `dev.dogwood.codegen` and `dev.dogwood:dogwood-host` by coordinate |
| `:guest` | the payload: one screen in Kotlin/JS, compiled, **signed**, served over HTTP | `dev.dogwood:dogwood-compose:0.1.0` — the published JavaScript artifact with the engine's guest stubs compiled in |
| `:app` | a desktop host that fetches, verifies and renders that payload | `dev.dogwood:dogwood-host:0.1.0`, plus the Zipline compiler plugin from Maven Central by coordinate |

`tools/standalone-check/run.sh` runs the whole path and **its verdict is a render, not a build**:
the app runs with `--check` and exits by what its render transcript recorded — the payload's marker
string detailed by a drawn `Text`, the product's *own* generated bindings (`UmbraBanner#`,
`UmbraStepper#` — components that exist nowhere in the Dogwood repository) as transcript lines, and
a non-zero measured box. The check's first run failed on the marker, which is how it earned belief.

```
UMBRA loaded version 1.0.0, verified by dogwood-development
UMBRA TRANSCRIPT 5 bindings
UMBRA CHECK PASS
```

## 3. Rationale & Research

**The first payload build outside the repository found a generator defect, on its first
compilation** — which is A2's argument, made by the build rather than by the audit. Umbra's
`UmbraStepper` declares `onChange: (Int) -> Unit`, the most ordinary shape a stepper, slider or
pager can have, and the classifier rejected it as an "indexed content lambda": a branch matching
any lambda containing `(Int)`, behind an operator-precedence slip, guarding against a case that
cannot reach it — an indexed *content* lambda is `@Composable` and becomes a slot two branches
earlier. The component had been silently unbindable for as long as it existed. The original
standalone check never noticed because nothing ever tried to **call** it from a guest; the stub
simply wasn't there, and a host binding with an event nobody can send compiles fine.

Fixed in `Parser.kt` — everything reaching `classifyLambda` and returning `Unit` is an event,
arguments included; the event machinery has carried positional serializable arguments since the
first holder report. `EventArgumentTest` pins it with both controls: the `@Composable (Int) -> Unit`
content case still classifies as a slot, and a value-returning lambda is still refused.

**Two more things an adopter learns from this build, now written where they write them:**

- `pluginManagement` needs `google()`: the Zipline Gradle plugin's own classpath reaches androidx
  artifacts that live on Google's Maven and nowhere else.
- The Zipline **compiler** plugin is added by coordinate
  (`app.cash.zipline:zipline-kotlin-plugin`), because outside the repository there is no version
  catalog to alias it from.

**The trust arrangement is the samples', on purpose.** The guest signs with the same well-known
throwaway development key the Dogwood samples commit (labelled as such), which lets `:app` trust
`DogwoodTrust.DEVELOPMENT_KEYS` from the published `dogwood-protocol` instead of carrying a key
copy. A real product replaces both ends — that is `DECISIONS-FOR-THE-OWNER.md` §6, not this sample.

## 4. Unstated Assumptions

- **A shared checkout is the one way this is weaker than a truly external build.** Equal in every
  way that has ever caught a defect here: publication metadata, module naming, plugin resolution,
  generated-source seams — and now the guest classifier.
- **The desktop host stands in for all three.** Umbra renders on the JVM; an external Android or
  iOS application build is not exercised (the engine's own samples cover those platforms, from
  inside).
- **The check needs a display.** `:app` opens a real window; the standalone check remains a local
  tool, as it always was.
- **Version pinning is the adopter's.** Umbra's root build declares Kotlin 2.3.20 / Compose 1.10.3 /
  Zipline 1.27.0 — matching the engine — and says so; the policy question is audit item A6.
