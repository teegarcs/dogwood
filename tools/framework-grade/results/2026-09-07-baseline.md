# Project Dogwood — Framework Report Card

**Evaluator's basis.** I read Dogwood's own documents and cross-checked them against its code and history: counted the 14 components in `engine/surface/dev/dogwood/surface/DesignSystemSurface.kt` (PrimaryButton through SnackbarArea — no dialog, sheet, menu, pager, or picker, exactly as its audit admits); counted 72 test files / 518 `@Test` annotations in `engine/`; read the generated conformance matrix in `plans/conformance.md`; read all of `plans/adoption-audit.md` and `OPEN-DECISIONS.md`; skimmed the 75 ADR files via `adrs/README.md`; verified the git history (**first commit 2026-08-30, last 2026-09-07, 174 commits, one contributor**). Performance and drill results are repo-recorded, internally cross-checked but not independently reproduced by me. Competitor state was researched against current sources (Sept 2026).

**One market fact reframes everything: Redwood is discontinued.** Cash App's 0.19.0 (Nov 2025) was announced as the final release; the README says the project is no longer under active development. Zipline itself remains healthy (1.27.0, Apr 2026, active commits). Dogwood is therefore now arguably the only *living* open-source "real code on device" SDUI stack — and its closest relative dying with Block-scale backing is also the most important data point about this niche's survival odds.

## Per-dimension analysis

### 1. Ease of adoption — Dogwood: D+
The documentation is genuinely excellent (getting-started assumes a real existing app; `samples-standalone/umbra` is a complete three-module product — design system, signed payload, rendering host — proven against published artifacts, ADR-057), but the artifacts publish to **`mavenLocal()` only** (`OPEN-DECISIONS.md` §5): today nobody outside a clone of this repo can resolve them at all. Add the hard constraint that your host must be a Compose Multiplatform application (ADR-004), and that iOS embedding into an existing app is "described and not built" — no framework/XCFramework target exists (audit B4). The docs earn a B+; the physical adoption path earns an F; D+ is the honest blend.
Others: *DivKit B+* (published artifacts, three platforms, playground, DSLs). *Redwood C−* (well-packaged but you'd be adopting an abandoned pre-1.0 framework). *RFW B−* (one `pub add` — then you build delivery, signing, and tooling yourself, and only if you're already Flutter). *Generic JSON C* (adoption cost = building it). *Beagle F* (flagship repo deleted; `beagle-android` archived Dec 2022). *WebView A−.*

### 2. Authoring ergonomics — Dogwood: A−
This is Dogwood's crown jewel and it's real, not aspirational: you write ordinary Kotlin Compose (`remember`, `LaunchedEffect`, `derivedStateOf` all genuinely execute — the real Compose runtime runs in the sandbox), autocomplete works because stubs mirror the real surface, your own composables need zero registration, `@Preview` works, hot reload exists (continuous dev-serve plus the shells' five-second manifest poll, with state carried across the swap — audit B2, closed), and a screen-test recipe uses only public API (`docs/authoring.md` §8). Build-time refusals name their replacement (`animateFloatAsState` → declared target). The minus: Dogwood's types are *not* androidx's, so moving screens between static and dynamic worlds is "a port, not a re-import" (its own words), and the preview cannot show skew degradation or input latency.
Others: *WebView A* (the industry's best inner loop). *Redwood B* (Compose logic, but hand-written `@Widget`/`@Property` schemas and per-platform widget bindings). *DivKit B* (server DSLs in three languages plus a playground — best of the data-only camp). *Generic JSON C+*. *RFW D+* (a bespoke `.rfwtxt` format with no loops and no expressions). *Beagle F.*

### 3. Flexibility & expressiveness — Dogwood: A−
The model is the strongest available anywhere open-source: the server can change **logic, state, and structure**, not just data — full Kotlin on device, guest-side conditionals, arbitrary composition, host-owned state holders for scroll/focus/text, animation as declared targets (one crossing, host interpolates — ADR-020), namespaced product design-system segments (ADR-046), host services with request/response (D11). The minus is the present tense: the committed catalog is 14 components, per-frame APIs are banned by design, registered/native-powered components still ride an app release, and only four of eight planned holder shapes exist (audit B1). The ceiling is an A; the floor you'd ship on today is not.
Others: *Redwood A−* (same model; hand-built widget sets). *WebView A*. *DivKit B* (expressions, triggers, timers, patches — the richest data-only option, but no arbitrary code). *Generic JSON C*. *RFW D+* (explicitly no logic; the README steers you elsewhere for it). *Beagle C−.*

### 4. Production readiness — Dogwood: C+
This grade is a fraction with a large numerator and a hollow denominator. The **machinery** is more complete than anything else in this table: Ed25519 signing with rehearsed key rotation (B1/B2, and Layer-3 ADR-001 caught that the old suite would have *failed* a real rotation); crash-loop quarantine, signed kill switch, last-known-good, forgiveness (H1–H6, ADR-049) — on by default after audit A3; runaway-payload bounds on by default, watched with hostile drills whose negative control hung (ADR-060); guest crashes routed and source-mapped after the probe found they were previously *unobservable* (ADR-059); the whole Android matrix graded against the R8-minified build (ADR-056); skew containment drilled on three real clients. No competitor's open-source offering matches this checklist — Zipline provides signing and atomic swap but nothing like the release guard.
The denominator: **zero production deployments, ever.** No artifact hosting, throwaway committed dev keys, payloads served from `localhost:8080`, no staged-rollout server (only a client-side cohort bucket), CI that *cannot block a merge* (branch protection returns 403), the web host unguarded, no Apple ruling on the entire iOS mechanism, and the project's own honest law — "the first run of anything finds a defect" — has never been applied to the one thing that matters most: a real fleet. Its own audit's verdict, which I endorse: "the adoption path has never been walked end to end."
Others: *WebView A−*. *DivKit B* (Yandex-scale production, active; delivery/rollback still yours to build). *Generic JSON B−* (data-only is inherently lower-risk: no code execution, no store-policy exposure; quality varies wildly). *Redwood C* (Zipline delivery proven at Cash App; the abandoned UI layer will never get another patch). *RFW C−* (renders bytes; everything else is your problem; no named production users). *Beagle F.*

### 5. Performance & footprint — Dogwood: C+
The measured numbers are good — recomposition p95 1.67 ms vs 8 ms budget, batch crossing 0.12 ms, cold start 128–155 ms vs 500 ms, GC p99 1.45 ms (`roadmap.md` Phase 0 table) — and the measurement discipline (positional encoding chosen on a four-order-of-magnitude garbage difference) is admirable. But **every number comes from fast hardware**; the low-end gate device was deliberately never acquired (ADR-008), G1–G4 read `·` on every client in the conformance matrix, and a 22.1 ms GC outlier remains unattributed. Interpretation cost bites hardest exactly on the low-end Android devices SDUI usually targets. The web leg is worse: **3,576,606 bytes brotli, 3/4 of it Skiko, 19.2 s to first frame on Fast 3G** (ADR-045) — Dogwood's own owner-decisions file concedes this is only fit for returning-user surfaces. Warm experiences cost 9–14 MB each (ADR-027).
Others: *Generic JSON A−* (native rendering, tiny payloads). *DivKit B+*, *RFW B+* (native/Flutter rendering, compact formats). *Redwood B−* (same QuickJS toll, but DOM on web — no Skiko). *WebView C.*

### 6. Platform coverage & consistency — Dogwood: B
Four targets (Android, iOS, desktop-as-dev-loop, web) from **one** generated binding against Compose Multiplatform, versus Redwood's four hand-written host implementations per widget — this is the architectural bet and it demonstrably works: the same screens run on all four (ADR-048), and the conformance matrix is the best parity *evidence artifact* I've seen from any framework, with honest per-cell gaps (D7 disabled-announcement missing on web; web network policy is browser CSP, explicitly recorded as weaker than mobile's default-deny; iOS wires no navigation service so J2/J4 are graded by nothing there). Held below B+ by: iOS has never faced App Review, desktop is explicitly not a shipping target, and web is a different beast operationally (no guard, no bounds, CSP-only).
Others: *RFW A−* within Flutter (pixel-identical by construction). *DivKit B+* (three mature platforms). *WebView A−*. *Redwood B−* (broad, parity manual). *Generic JSON C+* (hand-synced renderers drift — the classic failure). *Beagle F.*

### 7. Maturity, ecosystem & bus factor — Dogwood: F
Brutal, as instructed, and unavoidable: **the entire recorded history is nine days old** (2026-08-30 → 2026-09-07, 174 commits), one contributor, version 0.1.0 with an explicit "no stability promise," zero external adopters, zero production users, a private repo, artifacts that resolve from nobody's machine but the author's. The base rate is grim: Beagle, corporate-backed and at 2.0, vanished within two years; **Redwood, backed by Block with Jake Wharton on it, in this exact architectural niche, was discontinued at 0.19.0**. Dogwood's likelihood of being alive in three years is a function of one person's continued attention. The upstream dependency (Zipline) is healthy, which is the only structural mitigant.
Others: *WebView A+*. *DivKit B* (four years public, weekly releases, 33.x — but effectively one company, with geopolitical exposure some orgs can't accept). *RFW B−* (Google-official, visibly low investment, "best-effort" compatibility). *Generic JSON B−* (bus factor is your own org). *Redwood D* (explicitly dead; Zipline lives). *Beagle F.*

### 8. Maintainability of the system itself — Dogwood: A−
The strangest grade on the card: a nine-day-old project with the takeover documentation of a decade-old one. 75 ADRs that record not just decisions but the defects each first run found (the ADR index reads like an incident log: the render tests that were green on web while composing nothing, ADR-054; the classifier bug that made `UmbraStepper` unbindable its whole life, ADR-057; the eviction that freed nothing, ADR-027); a conformance catalogue whose matrix is generated from real runs and refuses a "fails-but-not-our-fault" verdict on principled grounds; `docs/checks.md` inventorying every check and what it proves; generated API docs that cannot drift; two files (`adoption-audit.md`, `OPEN-DECISIONS.md`) that state weaknesses more honestly than most projects' postmortems. A new team could take this over more safely than most 5-year-old codebases. Docked to A− because the merge gate is unenforced and the whole edifice reflects one mind's discipline with no second maintainer ever having tested whether it transfers.
Others: *WebView A*. *DivKit B*, *RFW B*. *Redwood C+* (good but frozen). *Generic JSON C*. *Beagle F.*

## Overall weighted verdict

Weights (a principal engineer betting a product): **Production readiness 25%, Maturity/bus factor 20%, Flexibility 15%, Ease of adoption 10%, Authoring 10%, Performance 10%, Platform coverage 5%, Maintainability 5%.**

- **DivKit: B+** — the sane default open-source choice today.
- **WebView: B+** — still the baseline to beat, and for web-heavy or first-visit surfaces it beats everyone.
- **In-house JSON SDUI: B−** — expensive to build, but yours; the pattern proven at Meta/Airbnb/Lyft scale.
- **Dogwood: C+** — a genuinely superior architecture and an exceptional engineering artifact, priced at an F in survival odds and a never-walked adoption path.
- **RFW: C+** — only within Flutter, only for trivially data-driven surfaces.
- **Redwood/Treehouse: C−** — adopting it today means adopting the abandoned; harvest its ideas (Dogwood did) rather than its code.
- **Beagle: F** — do not consider.

### Choose X if…
- **DivKit** — you want open-source SDUI in production this quarter, your screens are data-plus-light-logic, and Yandex provenance is acceptable to your org.
- **In-house JSON SDUI** — you have platform-team capacity, need SDUI on your highest-traffic surfaces for years, and want zero third-party survival risk.
- **WebView** — the surface is first-visit, content-shaped, or web-parallel anyway.
- **RFW** — you're all-in on Flutter and need only templated, logic-free remote screens.
- **Dogwood** — you would otherwise build Treehouse-class SDUI in-house, you can staff owning the engine outright (treat it as a fork-and-own acquisition, not a dependency), your surfaces are logic-rich and returning-user, and Android leads.
- **Zipline alone** — you want OTA Kotlin *logic* without OTA UI; it's alive and proven.

### Dogwood's 3 biggest genuine advantages
1. **The authoring model eliminates the mapper treadmill for composition.** Real Compose with real on-device state and logic; product composables ship free in the payload with no registry entry; both halves of the bridge generated from one surface file. Nothing else open-source offers this today — its only peer discontinued itself.
2. **The verification culture, and the un-ship story it produced.** Signed delivery with rehearsed rotation, crash-loop quarantine, signed kill switch, runaway bounds, source-mapped guest crashes, R8-graded matrix — each closed by *running the thing* and documented at the defect it found. This is a moat: reproducing this evidence discipline in-house would cost more than reproducing the code.
3. **One generated binding → four platforms, with parity evidence.** Rendering through Compose Multiplatform instead of per-platform native widgets is a real structural cost saving over Redwood's 4-bindings-per-widget, and the conformance matrix makes the parity claim checkable rather than asserted.

### Dogwood's 5 biggest genuine risks
1. **Existential:** one author, nine days of history, 0.1.0, unpublished artifacts, no adopters — in a niche where Block-backed Redwood just died. Any bet on Dogwood is a bet on owning it yourself.
2. **Apple:** the entire iOS mechanism (downloaded interpreted payloads under Guideline 4.7) has no written ruling and has never been submitted to review; and no iOS embedding artifact even exists (audit B4). The Zipline precedent is strong but unwritten.
3. **Performance is unproven where it matters:** every budget graded only on fast hardware, the gate device deliberately not acquired (ADR-008), a 22.1 ms GC outlier unattributed — and low-end Android is SDUI's home turf.
4. **The catalog is a slice:** 14 components, no dialog/sheet/menu/pager/picker; a real product's first milestone is building its design system on four promised-but-unproven holder shapes; multi-team payloads (B3) unexamined; toolchain triple-coupling has a policy but no cross-version drill yet (A6 half-open).
5. **Operationally, the back half doesn't exist:** no hosting, no production keys or rotation procedure, no rollout server, localhost serving, CI that can't block a merge — plus a web leg (3.58 MB, CSP-only, unguarded) fit only for returning-user surfaces.

### What you'd have to believe
**…for Dogwood over JSON SDUI:** that your dynamic surfaces need on-device *logic and interaction depth* (forms, optimistic state, conditional flows) that data-only payloads can't express without server round-trips; that the component-mapper treadmill would cost you more over 3 years than owning a young engine; that you can absorb interpreter overhead on your device fleet and App Store policy risk on iOS; and that you'll staff Dogwood as your own code with its author's discipline. If your screens are promos, feeds, and settings — you don't need this; take DivKit or build JSON.

**…for Dogwood over raw Redwood/Treehouse:** less than you'd think, because Redwood's discontinuation did most of the arguing — "raw Treehouse" now means forking an abandoned pre-1.0 framework anyway, so both paths are fork-and-own. The residual beliefs: that Compose-Multiplatform-as-sole-renderer (one generated binding, host-must-be-CMP) beats Redwood's native-widget mapping (four hand bindings, native look); that generating the bridge from the API surface beats hand-writing schemas; and that Dogwood's additions Redwood never had — the release guard, the conformance matrix, the skew containment, runaway bounds — are worth trading away Cash App's years of production hardening for nine days of one very careful person's work. The first two are credible engineering arguments; the third is the entire bet.
