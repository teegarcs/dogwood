## Per-dimension analysis (Dogwood evidence = file paths; competitors = today's research)

### 1. Ease of adoption — D+ (unchanged)
The rubric's D anchor is explicit: "artifacts unresolvable outside the repository," and that is still the fact — `samples-standalone/umbra/settings.gradle.kts` resolves everything from `mavenLocal()`, per `OPEN-DECISIONS.md` §5. Everything *around* the locked jaw has improved since baseline: Umbra is now a whole product (design/guest/app, signed payload, render-transcript verdict — `tools/standalone-check/run.sh` fails on "did not render," verified); the iOS embedding artifact now exists (`engine/samples/ios-embed` builds `DogwoodEmbed.xcframework`; `tools/ios-embed-check/run.sh` asserts both slices and the exported Swift factory — audit B4 closed); `docs/README.md` is a real front door; the import migrator lowers the entry port. But nobody outside a clone of this repo can `implementation("dev.dogwood:...")` anything, and the host must be a Compose Multiplatform app (ADR-004). Docs B+, physical path F, blend D+.
**Cheapest one-step raise:** publish the five artifacts + plugin to any resolvable repository (even GitHub Packages) — with E4 done, that alone opens B territory.

### 2. Authoring ergonomics — A− (unchanged)
Verified rather than believed: ordinary Kotlin Compose with real `remember`/`LaunchedEffect`; `@Preview` genuinely works with an honestly stated caveat (`developer-experience.md` line 116 — it cannot show skew degradation or input latency); hot reload = continuous webpack + the shells' 5-second manifest poll with state carried (audit B2, closed); a screen-test recipe against public API in `docs/authoring.md` §8; and new since baseline, `tools/import-migrator/migrate.py`, which rewrites the one-for-one imports and marks each real API difference with a `// MIGRATE:` line instead of guessing (its docstring is explicit about refusing to translate call sites — the right call). The residual hole is the B-anchor's own example: migration is still a port at call sites, by design (`PrimaryButton(label=…)` vs `Button {…}`). One partially-closed hole against an otherwise-A row: A−.
**Cheapest raise:** none cheap — near-mechanical migration needs API-shaped wrappers, which the wire format deliberately forbids.

## Choose X if…
- **DivKit** — you want open-source SDUI in production this quarter, data-plus-light-logic screens, and Yandex provenance clears your org. It released twice in the week of this grading.
- **In-house JSON SDUI** — you have platform-team capacity and want zero third-party survival risk; it's the pattern every proof-at-scale system chose.
- **WebView** — first-visit, content-shaped, or web-parallel surfaces. On Dogwood's own web numbers, a WebView beats it outright there.
- **RFW** — all-in on Flutter, logic-free templated screens only.
- **Zipline alone** — OTA Kotlin *logic* without OTA UI; alive and proven.
- **Dogwood** — you would otherwise build Treehouse-class SDUI in-house, you staff it as a fork-and-own acquisition, your surfaces are logic-rich and returning-user, Android leads, and you accept betting on one author's nine-day-old engine because you intend to become its second author.

## Dogwood's top advantages
1. **The authoring model is real and unmatched**: actual Compose with on-device state and logic, both halves of the bridge generated from one surface file, product composables free of registry cost. Its only architectural peer discontinued itself ten months ago.
2. **The un-ship and evidence machinery**: signed delivery with rehearsed rotation, quarantine/kill-switch/last-known-good on by default on all four clients, runaway bounds, source-mapped guest crashes, R8-graded matrix, frozen cross-version fixture — each closed by running the thing and documented at the defect the run found.
3. **One generated binding → four platforms, with a per-claim, per-client evidence system** (`claims.tsv` + generated matrix) that is the best parity instrument I have seen in any framework, open or closed.

## Dogwood's top risks
1. **Existential**: one author, nine days, unpublished, zero adopters, in a niche where Block-backed Redwood just died. Every other risk is downstream of this one.
2. **Apple**: no written ruling on downloaded interpreted payloads (Guideline 4.7), never submitted to review (`OPEN-DECISIONS.md` §2).
3. **Performance unproven where SDUI lives**: G1–G4 ungraded on every client; low-end Android untouched (ADR-008).
4. **The floor is thin**: 16 components; menu/pager/pickers absent; multi-team payloads (B3) unexamined; a product's first milestone is building its design system.
5. **The operational back half is a reference, not a deployment**: throwaway keys, localhost serving, advisory CI — all owner-gated, exactly as `plans/score-improvement.md`'s arithmetic predicted.

## What you'd have to believe
**…for Dogwood over JSON SDUI:** that your dynamic surfaces need on-device logic and interaction depth data-only payloads can't express; that the mapper treadmill costs more over three years than owning a young engine; that you can carry interpreter overhead on your fleet and Apple-policy risk on iOS; and that you will staff it with its author's discipline — the stale-matrix slip this run found is what one week without that discipline looks like.
**…for Dogwood over the Redwood lineage:** less than before — Redwood's discontinuation (re-verified: final release 0.19.0, Nov 2025) makes both paths fork-and-own. Residual beliefs: one generated Compose Multiplatform binding beats four hand-written native ones; generating the bridge from the API surface beats hand-written schemas; and the release guard + conformance system + skew containment are worth trading Cash App's years of production hardening for nine days of one very careful person's work. The first two are credible engineering arguments with evidence in this repo; the third is the entire bet, and it is an F-grade bet by this rubric's own definition.
