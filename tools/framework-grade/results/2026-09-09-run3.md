## 2. Per-dimension analysis

### 1. Ease of adoption — D+

Documentation is the best in the comparison set. `samples-standalone/umbra/` is a genuinely separate
Gradle build — no `includeBuild`, no path into `engine/` — that generates its own dictionary segment,
compiles a payload against published artifacts, signs it, serves it and **renders** it, with
`tools/standalone-check/run.sh` taking the render transcript as the verdict rather than a green
build.

Two hard facts sit under that. **Artifacts resolve from `mavenLocal()` and nowhere else**, which is
the D anchor verbatim. And, new this run: **`dogwood-host` publishes no Android variant** —
`androidTarget` is declared at `build.gradle.kts:24` but `publishLibraryVariants` is never called, so
the published metadata carries `common, jvm, native, wasm` and no `androidJvm`. An Android consumer
falls through onto `dogwood-host-jvm`, whose class files are major version 65 (Java 21) against the
module's own `JVM_11` request. There is no `androidMain` source set, so the fallback is
code-identical and may work — but nobody has tried, because the only outside-the-repo consumer is a
desktop application.

iOS is genuinely better: `engine/samples/ios-embed` produces a real `DogwoodEmbed.xcframework` with
device and both simulator slices, and its check states its own limit (header inspection, not a
compiled Swift app).

*Cheapest raise:* publish anywhere resolvable **and** add `publishLibraryVariants("release")`.

### 2. Authoring ergonomics — B+ (was A−)

You write ordinary Kotlin Compose with full IDE support, because it *is* Kotlin. The inner loop is
better than advertised: `--continuous` plus every shell host's five-second poll, carrying
`rememberSaveable` state across the swap — the production code-update machinery doubling as hot
reload. Screen tests use only public API and the real decoder.

Two holes, and they are exactly the rubric's two named B-anchor examples. **Migration is a port**,
stated plainly in `docs/authoring.md` §9. **There is no preview**: `developer-experience.md` claimed
`@Preview` works, and `dogwood-compose` declares `js(IR)` and nothing else, so guest screens cannot
compile for the JVM and no preview pane can render them.

Thirteen `Modifier` extensions exist engine-wide — no `clickable`, no `border`, no `offset`.

**This is a re-anchor, not a regression.** Nothing got worse; the A anchor requires previews *and*
near-mechanical migration, and neither holds.

*Cheapest raise:* give `dogwood-compose` a JVM target so `@Preview` renders — or delete the claim.

### 3. Flexibility and expressiveness — B+

The **ceiling** is the best in the field and is built rather than promised: the real
`androidx.compose.runtime` runs in QuickJS, so the server delivers logic, state and structure.
Extension is proven from outside the repository — Umbra registers its own segment and renders through
generated bindings with zero engine change.

The **floor** is what the rubric grades: 20 surface components plus 12 engine primitives, 8 holder
shapes. Thirty-two bindable widgets against a product design system's fifty to two hundred.
`docs/authoring.md` §10 names what is structurally absent. That is the B anchor word-for-word — "a
full-logic model with a thin catalogue" — lifted to B+ by a cheap, externally-proven extension
mechanism.

*Cheapest raise:* thirty more components. No shortcut; the machinery is proven and the work is volume.

### 4. Production readiness — C+

The machinery is more complete than most systems actually in production: Ed25519 signing with
rotation on four clients (web via a signed detached sidecar verified before the document is parsed),
pre-flight refusal of a too-new payload on three, kill switch and crash-loop quarantine with the
device half observed on a real emulator, runaway bounds on by default whose negative control *hung
rather than failed*, source-mapped crashes on mobile and ten real frames on web, the whole
instrumented suite running on the R8 release build with zero engine keep rules, a reference server
with cohort rollout and resume, and cross-version claims against a frozen signed fixture.

What caps it: **nothing has ever run in production** (the rubric's C+ cap), no production keys and no
hosting, no Apple ruling, and a merge gate that cannot block — and which is **red on `main` right
now**, two of the last three pushes having failed unnoticed while the document describing the gate
says it has been green on every merge.

**New finding: "sandbox" is asserted where the substrate disclaims it.** Zipline's own README states
it "does not offer a sandbox or process-isolation and should not be used to execute untrusted code."
Dogwood uses the word twelve times across its README and specs, and no threat model exists anywhere
in the repository. The actual posture — first-party signatures, default-deny network, value clamping,
containment — is coherent and well-built. It is trust-by-signature, not isolation, and a security
reviewer will ask on day one.

*Cheapest raise:* real keys plus real hosting. Production itself is the only route past B.

### 5. Performance and footprint — C+ (at the rubric's cap)

The measurement culture is exceptional for a project this age: a six-encoding wire-format bake-off, a
render-strategy decision made on scaling rather than latency, GC pause attribution through public API
without patching QuickJS.

Capped correctly — every number comes from an Apple-silicon Mac, an emulator, or a Pixel 10 Pro, and
`G1`–`G4` read `·` on every client. The new evidence makes the cap look generous: ADR-064 found `G1`
met at four emulator cores and missed at one, with steady-state flat and every tail 2–6× worse. **The
headroom was parallelism.**

Footprint is the worst number in the set: 3,766,502 bytes brotli on first web visit, ~70% Skiko,
19.2 s on Fast 3G. The budget raise to 3.90 MB arrived with byte-level attribution under a rule
requiring the same of every future raise.

*Cheapest raise:* one 2022-tier Android device, one Phase 0 run. The grading is already wired.

### 6. Platform coverage and consistency — B+

Three shipping clients plus desktop as a declared development loop, from one set of screens. The
evidence quality is the best in the set and it is structural: ~60 numbered claims in a written
catalogue, and a matrix **generated** by `aggregate.py`. Regenerated from the committed raw runs it
reproduces exactly — android 65/4 skip, desktop 44, ios 64/4, web 59/1, zero failures.

Honest cells everywhere, each with a written reason. Deductions: three platforms against DivKit's
three-at-scale; unquantified App Store risk on iOS; web's network policy is the browser's CSP,
recorded as weaker rather than equal.

One drift: Part 3 carried **two** summary blocks, the second stale, in a section headed "Do not edit
by hand."

*Cheapest raise:* one line of navigation service in the iOS sample closes `J2`/`J4`.

### 7. Maturity, ecosystem and bus factor — F

Ten days old, 165 commits, one human contributor, private repository, `mavenLocal()` only, version
0.1.0 with no stability promise, zero adopters. The rubric: "A single-contributor unpublished 0.x
project is an F here whatever else is true." Every clause holds at once, and 20% of the card sits
here.

**The substrate risk compounds it.** Zipline is alive — it shipped a Kotlin 2.4.20 upgrade the day of
this run — but 80 of its last 100 commits are Renovate bot, effectively one human maintainer is
active, and community crash fixes have been open since July and August 2026. Dogwood's bus factor of
one sits on a substrate with a bus factor of one.

*Cheapest raise (worth +0.20):* make the repository public and publish `0.1.0` somewhere resolvable.
One afternoon, worth more than the entire engineering backlog.

### 8. Maintainability of the system itself — A−

A new team could take this over. 81 ADRs with an index recording what *running things* found, five
layer specs with 12 Mermaid diagrams, ~196,000 words of core documentation a quarter of it generated
so it cannot drift. Verified cheaply: link-check green over 139 files, render-shape green over 10,
the surface measurement reproduces the README's classification, and
`:dogwood-host:jvmTest :dogwood-codegen:test --rerun-tasks` → **1003 tests, 0 failures**.

The policies bite. Every drill carries a negative control; a drill that cannot run *refuses*; a red
claim is validated before it is believed. Three times in the recent record a "closure" turned out
worse than the finding once actually run — crashes were *unobservable* rather than unreadable, the
runaway-loop control *hung*, the desktop skew drill was *passing while testing nothing*. That pattern
is the strongest quality signal on this card.

Deductions, all documentation-versus-code drift at a commit titled "Bring the documentation back in
line with what the code does": the false `@Preview` claim, three risk-register items still marked
open that ADRs resolved, the duplicated stale matrix block, the unexamined "sandbox" claim, and a
gate that cannot block and is currently red.

*Cheapest raise:* an enforceable merge gate — which also buys dimension 7.

## 3. Competitor evidence (re-researched 2026-09-09)

**Zipline + Redwood/Treehouse — the two halves have diverged.** Redwood's README says "This project
is no longer under active development." Release 0.19.0 (2025-11-06) was **never published to Maven
Central** — repo1 stops at 0.18.0 — and the final release exists only as a Git tag. Exactly one
commit in all of 2026. No fork has traction. Zipline itself is alive (1.27.0, pushed the day of this
run) but on one active human maintainer. **The production folklore is thinner than the field
believes:** Redwood's own author wrote in 2023 that "our usage of Redwood to date has been very
limited," and JetBrains' Cash App case study never mentions Zipline, Redwood or server-driven UI —
noting instead that Cash App abandoned a JavaScript runtime for server-driven logic in favour of KMP.
To Dogwood's credit, its ADR-003 does not overclaim this precedent.

**DivKit — the healthiest dedicated SDUI framework in existence.** 33.2.0 released 2026-09-08,
mirrored to four package managers within 24 hours; 100+ commits in 30 days from 20 authors;
Apache-2.0. Logic model is the rubric's B anchor exactly — typed variables, expressions with
fallback, user-defined functions, triggers — with no scripting runtime, no loops, no statements.
Risks are governance: a Yandex-entity Contributor License Agreement, no named Western adopter, an
abandoned Flutter client.

**Beagle — deader than "unmaintained."** The monorepo returns HTTP 404, the split repos were archived
2025-04-17, and `usebeagle.io` has no DNS A record, so every documentation link in the surviving
READMEs is dead. No deprecation notice was ever published.

**Flutter RFW — a correction to the received wisdom.** The famous "experimental… might be abandoned"
warning **was removed in February 2026**; current text says "relatively stable." But the feedback
issue was closed after four years, and 1.1.0 added exactly one widget in a year. Its README states
its own ceiling with unusual clarity: "you will slowly be tempted to move your whole application to
this model. **This won't work.**" A new component means an App Store release.

**AndroidX Remote Compose — added to the set, and the thing to watch.** `androidx.compose.remote`,
Apache-2.0, AOSP. alpha01 2025-12-17 through alpha19 landing the day of this run — nineteen releases
on a strict two-week cadence with zero skips. Clean split between creation (plain JARs, so
server-side authoring works) and playback. **The disqualifier today: every player artifact is `aar`.
There is no iOS player.** It scores a hair above Dogwood, and it is Google building Dogwood's
premise.

**Ruled out, with reasons.** Lynx is an RN/Flutter competitor, not SDUI. Hyperview is maintained,
pre-1.0 after eight years, at 1,283 npm downloads/month. Ionic Portals **cannot be bought** — new
commercial sales discontinued 2025-02-11. React Server Components in React Native are labelled
experimental by Expo's own docs. Skip.tools is build-time transpilation with no remote-UI capability.
Expo EAS Update is not SDUI but is frequently the correct answer to the underlying problem, at three
to four orders of magnitude more adoption than every framework here.

**Closed-source proof-at-scale — and the headline is not who you would expect.** The strongest public
evidence is **Nubank's Catalyst**: >115M customers, >90% of screens, >14,000 distinct screens, lead
time from weeks to ~20 minutes — delivered by **a tree-walk interpreter in Flutter, "around 500 lines
of code or less," evaluating six expression types from JSON**. Meta's Bloks is the largest by user
count and the worst documented. Airbnb's Ghost Platform has one post in five years. **Netflix scoped
it deliberately narrow**, verbatim: "Netflix only delivers UMA with these server-driven UIs."
DoorDash kept stateful and animated components client-driven. Lyft still says "We don't have a single
framework to build SDUI at Lyft yet." **And the cautionary tale is Uber's Screenflow**: a
TypeScript-subset DSL compiled to an IR, fourteen engineers, 2017–2020, sixteen flows in production,
then the department was shut down.

## 4. Choose X if…

- **In-house JSON SDUI** if your dynamic screens are merchandising, promos, lists, forms and
  messaging. Nubank proves the category reaches >90% of screens. **3.04 is not a consolation prize —
  it is the field's answer.**
- **DivKit** if you want that without building it and can clear a Yandex-entity CLA through
  procurement. Highest live score in the set.
- **The WebView** if page weight and startup are acceptable and your team is already a web team. It
  wins this rubric outright and is chronically underrated.
- **Flutter RFW** only if your app is Flutter and you accept that a new component means a store
  release.
- **Zipline directly, without Redwood**, if you want server-delivered Kotlin *logic* rather than UI.
  Highest value, lowest risk slice of the whole idea, on a substrate that still ships.
- **Watch AndroidX Remote Compose** if you are Compose-based and can wait.
- **Dogwood** if you are a Compose-Multiplatform-native organisation on all three platforms, have
  genuinely hit the component-mapper treadmill, need server-delivered logic and structure rather than
  data, your web surface tolerates 3.8 MB on first visit, **and you intend to be its second
  maintainer**.
- **Not Beagle.** The repository 404s and the docs domain has no DNS record.

## 5. Top advantages

1. **The bridge is generated from one parse, both halves — and proven from outside the repository.**
2. **Server-delivered logic, not data.** Only the Redwood lineage and the WebView are in this class,
   and one of them is dead.
3. **The un-ship story is more complete than most production systems'.**
4. **Evidence discipline that is genuinely rare at any age** — generated matrix over a written
   catalogue, negative controls as policy, refusal distinguished from failure, three recorded cases
   where running the thing found the closure was *worse* than the finding.
5. **It tells you what it cannot do.**

## 6. Top risks

1. **Bus factor one, ten days old, zero adopters, unpublished** — on a substrate with one active
   maintainer.
2. **The tail budget is met by parallelism, not margin**, and the device that would settle it will
   not be acquired.
3. **No Apple ruling.** 4.7 is the right anchor and the JavaScript framing helps, but nothing is in
   writing.
4. **A thirty-two-widget floor.** The first milestone of adoption is building a design system.
5. **The Android artifact is not published and the path is unexercised.**
6. **3.77 MB brotli / 19.2 s Fast 3G on first web visit.**
7. **The gate cannot enforce and is red right now.**
8. **"Sandbox" is asserted where the substrate disclaims it**, with no threat model written down.

## 7. What you'd have to believe

### (a) …to choose Dogwood over an in-house JSON SDUI

1. **That your dynamic screens need logic, not data** — and that Nubank is the exception. If a
   500-line interpreter gets you 90%, the marginal value of a full Compose runtime in QuickJS is the
   last 10%, and you are paying an interpreter, signing, quarantine and 3.8 MB for it.
2. **That the mapper treadmill is your actual bottleneck.** You are trading a bounded recurring cost
   for a bounded one-time cost somebody else already paid.
3. **That you can be a Compose Multiplatform organisation on all three platforms.** ~9 MB on iOS,
   Skia rather than native widgets, and an iOS team's written yes. Redwood asked less and reportedly
   could not get it.
4. **That the industry's scoping instinct is wrong.** Every organisation with the resources to build
   what Dogwood builds chose to build less.
5. **That you will staff it.**

### (b) …to choose Dogwood over the Redwood lineage

1. **That "one generated binding instead of four hand-written ones" is worth the Compose
   Multiplatform constraint** — which is the exact organisational ask Redwood's adoption reportedly
   foundered on, made larger.
2. **That Redwood's shutdown was about Cash App, not the category.** The most charitable reading is
   that this category does not survive a reorg, which is a fact about economics rather than code.
3. **That losing production evidence is acceptable** — and here the research cuts toward Dogwood:
   **the Redwood lineage never had the at-scale proof the field attributes to it.** You are not
   giving up proven ground, but neither of you has any.
4. **That Skia rendering is acceptable where Redwood gave you native widgets** with real platform
   accessibility. Dogwood inherits Compose Multiplatform's, which its own matrix records as
   incomplete on web.
5. **That building beats forking.** Forking Redwood at 0.18.0 gives a four-platform system on a
   substrate that still ships releases. **This repository does not evaluate that alternative
   anywhere, and it should.**
